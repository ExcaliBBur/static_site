# T5. Публикуемость и цитируемость результата

Задача T5 — определить, что отличает «сайт с результатами» от полноценной
публикации, и какие механизмы для этого дают генераторы из T1:
**MkDocs + Material**, **Sphinx + MyST**, **Pelican** и **Quarto**.

Для каждого механизма используется трёхуровневая шкала:

| Обозначение | Смысл |
|---|---|
| **К** — из коробки | работает штатными средствами генератора или его основной темы, достаточно настройки |
| **П** — плагин | нужен сторонний пакет/расширение, устанавливаемый из PyPI |
| **Р** — вручную | нужен собственный шаблон, статический файл, внешний сервис или организационное правило |

Все утверждения вида «К/П/Р» для MkDocs и Sphinx проверены на практике в этом
репозитории (см. раздел «Реализация в проекте» ниже); для Pelican и Quarto —
по официальной документации.

## 1. Постоянные ссылки и стабильность URL

Постоянная ссылка — это URL, который не меняется при пересборке и
реорганизации сайта. У всех рассмотренных генераторов URL страницы выводится
из пути к исходному файлу, поэтому **пересборка сама по себе URL не меняет**:
изменения происходят при переименовании файла, смене структуры каталогов или
переключении режима формирования адресов.

| Генератор | Откуда берётся URL | Типичная ловушка | Редиректы со старых адресов |
|---|---|---|---|
| MkDocs | путь к `.md`; `use_directory_urls` превращает `a/b.md` в `a/b/` или `a/b.html` | переключение `use_directory_urls` меняет **все** адреса сайта | П: `mkdocs-redirects` (HTML-страницы с `meta refresh`) |
| Sphinx | имя документа (`docname`) + `.html`; `dirhtml`-билдер даёт `a/b/` | смена билдера `html` ↔ `dirhtml` | П: `sphinx-reredirects` |
| Pelican | шаблоны `ARTICLE_URL`/`ARTICLE_SAVE_AS` и метаданное `slug` | slug по умолчанию выводится из заголовка — правка заголовка меняет URL | Р (или плагин) |
| Quarto | путь к `.qmd` | переименование файла | К: поле `aliases:` в заголовке документа |

Якоря внутри страницы менее стабильны, чем адреса страниц: они выводятся из
текста заголовков, и при правке заголовка ссылка вида `page.html#раздел`
начинает вести на начало страницы. Поэтому для цитируемых мест (таблиц,
рисунков, формул) следует задавать **явные идентификаторы**: в Sphinx это
метки `(label)=` и `:name:`, в MkDocs — атрибуты `{#id}` и `attrs: {id: …}`.
В этом проекте все объекты, на которые ссылается текст, имеют явные id
(`tab-results`, `fig-static`, `eq:mse`/`eq-mse`, `lst-gd`).

Режим `mkdocs build --strict` с `validation.anchors: warn` проверяет
существование якорей при каждой сборке, т. е. «битая» внутренняя ссылка
не попадёт в публикацию. В Sphinx ту же роль выполняет флаг `-W` и встроенный
`linkcheck` для внешних ссылок.

**Вывод.** Стабильность URL — прежде всего организационная политика
(не переименовывать опубликованные страницы, фиксировать режим URL), генератор
лишь помогает её соблюдать: проверкой ссылок при сборке и редиректами.

## 2. Версионирование сайта и соответствие версий сайта, кода и данных

Опубликованный результат должен однозначно отвечать на вопрос «из какого кода
и каких данных получено это число». Для этого нужны две вещи:

1. **Несколько версий сайта одновременно** (`/v1.0/`, `/v1.1/`, `/latest/`),
   чтобы старая ссылка продолжала показывать старые результаты.
2. **Метка происхождения на каждой странице**: хеш коммита, дата сборки,
   версия набора данных.

| Механизм | MkDocs + Material | Sphinx | Pelican | Quarto |
|---|---|---|---|---|
| Несколько версий, переключатель | П: `mike` + К: селектор версий в Material (`extra.version.provider: mike`) | П: `sphinx-multiversion` (или хостинг Read the Docs) | Р: отдельные каталоги | Р: отдельные каталоги / профили проекта |
| Номер версии в шаблоне | Р: `extra` в `mkdocs.yml` | К: `version`/`release` в `conf.py` | Р | К: `version` в метаданных |
| Дата последнего изменения страницы | П: `git-revision-date-localized` | К: `html_last_updated_fmt`; П: `sphinx-last-updated-by-git` | К: `modified` в метаданных | К: `date-modified` |
| Хеш коммита / версия данных | Р | Р | Р | Р |

В проекте метка происхождения формируется скриптом `scripts/prepare.py` и
выводится на главной странице и странице стресс-теста обоих сайтов:
`Коммит <sha> · сборка <дата UTC> · набор данных v1.0 (sha256 …)`.
Хеш набора данных хранится в `data/dataset.meta.json` и пересчитывается
при изменении `dataset.csv`, поэтому расхождение данных и опубликованного
графика видно сразу.

## 3. DOI и ORCID

**DOI не создаётся генератором.** Правильная схема — архивировать
зафиксированную версию репозитория в Zenodo:

1. Репозиторий подключается к Zenodo (GitHub → Zenodo integration).
2. Создаётся git-тег и GitHub Release (`v1.0.0`).
3. Zenodo по вебхуку забирает архив релиза, присваивает **DOI версии** и
   общий **concept DOI**, всегда указывающий на последнюю версию.
4. Метаданные записи (авторы, ORCID, лицензия, ключевые слова) Zenodo берёт
   из `.zenodo.json` или из `CITATION.cff` в корне репозитория.

Файл `CITATION.cff` в этом репозитории одновременно включает кнопку
«Cite this repository» на GitHub и служит источником метаданных для Zenodo.
DOI должен указывать на **лендинг Zenodo**, а не на сайт: у Zenodo есть
гарантия хранения, а адрес учебного хостинга может исчезнуть.

**ORCID** — идентификатор автора, который снимает неоднозначность имени.
Он указывается в `CITATION.cff` (поле `orcid`), в мета-теге
`citation_author_orcid` и в видимой подписи автора.

| Механизм | MkDocs + Material | Sphinx | Pelican | Quarto |
|---|---|---|---|---|
| DOI версии | Р (Zenodo) | Р (Zenodo) | Р (Zenodo) | Р (Zenodo); К: поле `doi:` выводится в блоке цитирования |
| Блок «Как цитировать» с BibTeX | Р | Р | Р | К: `citation: true` генерирует блок и BibTeX |
| ORCID автора | Р: шаблон | Р: шаблон | Р: шаблон | К: `author: - orcid:` |

## 4. Метаданные для индексации

| Механизм | Назначение | MkDocs + Material | Sphinx | Pelican | Quarto |
|---|---|---|---|---|---|
| Highwire Press (`citation_*`) | индексация Google Scholar | Р: override `extrahead` | Р: шаблон `page.html` | Р: шаблон | К: `google-scholar: true` |
| Dublin Core (`DC.*`) | библиотечные каталоги, репозитории | Р: override | Р: шаблон | Р: шаблон | Р: `include-in-header` |
| Open Graph (`og:*`) | превью в соцсетях и мессенджерах | К: плагин `social` темы Material (генерирует и карточки) | П: `sphinxext-opengraph` | П: плагин из `pelican-plugins` | К: `open-graph: true` |
| `<meta name="description">` | сниппет поисковика | К: `site_description`, `description` в front matter | К: директива `meta` | К: `summary` | К: `description` |
| `sitemap.xml` | обход сайта роботами | К: формируется всегда, нужен `site_url` | П: `sphinx-sitemap` | П: `pelican-sitemap` | К: при заданном `site-url` |
| `robots.txt` | правила обхода | Р: статический файл | Р: `html_extra_path` | Р: `STATIC_PATHS` | Р: `resources` |
| Канонический URL (`rel=canonical`) | борьба с дублями (GitHub Pages + Helios) | К: из `site_url` | К: `html_baseurl` | К: `SITEURL` | К: `site-url` |

Особенность, проверенная на практике: **канонический URL и sitemap
зависят от базового адреса**. Один и тот же сайт публикуется на GitHub Pages и
на Helios, поэтому `site_url` (MkDocs) и `html_baseurl` (Sphinx) задаются
переменными окружения в workflow, и каждое зеркало собирается со своим
адресом. Проверка показала, что это обязательно: обычные страницы MkDocs
ссылаются на ресурсы относительными путями и работают из любого каталога,
но `404.html`, `rel=canonical` и `sitemap.xml` строятся от `site_url`.
При сборке зеркала для Helios с адресом GitHub Pages страница 404
запрашивала бы стили по пути `/p2-static-site/assets/…`, которого на Helios нет.
Побочный эффект — у двух зеркал разные канонические адреса, и поисковик
может счесть их дублями. Правильное решение — отдельная переменная для
`rel=canonical` (всегда адрес основного сайта) при `site_url`, равном
фактическому адресу зеркала; в проекте оно не реализовано, основной
адрес — GitHub Pages.

Пример фактически сгенерированных тегов (MkDocs, страница стресс-теста):

```html
<meta name="citation_title" content="Сравнение генераторов статических сайтов …">
<meta name="citation_author" content="ExcaliBBur">
<meta name="citation_author_orcid" content="https://orcid.org/0000-0000-0000-0000">
<meta name="citation_publication_date" content="2026/09/29">
<link rel="schema.DC" href="http://purl.org/dc/elements/1.1/">
<meta name="DC.title" content="Стресс-тест научного контента … — Публикация результатов экспериментов">
<meta name="DC.rights" content="https://creativecommons.org/licenses/by/4.0/">
<meta property="og:type" content="article">
<link rel="license" href="https://creativecommons.org/licenses/by/4.0/">
```

Ограничение Highwire Press: Google Scholar индексирует прежде всего
страницы, похожие на статьи (заголовок, авторы, дата, PDF по
`citation_pdf_url`), и значительно лучше — на доменах научных организаций и
репозиториев. Мета-теги необходимы, но не достаточны; для реальной
индексации надёжнее Zenodo.

## 5. Лицензирование

Текст, код и данные — разные объекты авторского права, для них подходят
разные лицензии:

| Объект | Лицензия в проекте | Почему |
|---|---|---|
| Текст, рисунки, таблицы | CC BY 4.0 (`LICENSE-CONTENT`) | стандарт для научных публикаций, требует только указания авторства |
| Код скриптов, конфигурация, workflow | MIT (`LICENSE`) | CC-лицензии не предназначены для ПО (нет положений о патентах и об отказе от гарантий на код) |
| Данные | CC0 1.0 (`data/LICENSE`) | синтетические данные; CC0 снимает вопрос о «цепочке атрибуции» при агрегации |
| Сторонние файлы | исходные лицензии (MathJax — Apache 2.0, Plotly.js — MIT) | обязаны сохраняться при распространении |

Ни один генератор не управляет лицензиями «из коробки», кроме Quarto
(поле `license:` выводит лицензию в приложении к документу). В MkDocs и
Sphinx лицензия выводится через `copyright` в подвале (К), а машиночитаемая
ссылка `<link rel="license">` добавлена шаблоном (Р).

## 6. Соответствие принципам FAIR

Принципы FAIR [Wilkinson et al., 2016] сформулированы для данных, но
применимы к любому исследовательскому результату.

| Принцип | Требование | Чем обеспечено в проекте | Роль генератора |
|---|---|---|---|
| **F** — Findable | постоянный глобальный идентификатор, богатые метаданные, индексируемость | DOI через Zenodo (план), `CITATION.cff`, Highwire/DC/OG-теги, `sitemap.xml` | частичная: sitemap, meta, стабильные URL |
| **A** — Accessible | доступ по стандартному протоколу, метаданные доступны даже без данных | HTTPS на GitHub Pages; архив в Zenodo переживёт сайт | минимальная: генератор лишь создаёт статический HTML |
| **I** — Interoperable | открытые форматы, стандартные словари | CSV + JSON-метаданные, BibTeX, Dublin Core, CFF | частичная: форматы вывода |
| **R** — Reusable | лицензия, происхождение (provenance), описание метода | раздельные лицензии, метка коммита и версии данных, скрипт `prepare.py` | частичная: вывод метки версии |

FAIR — свойство всей системы публикации (репозиторий + архив + сайт),
а не одного генератора.

## 8. Что достижимо при размещении на Helios

Helios — учебный сервер ИТМО: файлы из `~/public_html` пользователя
отдаются веб-сервером по адресу `https://se.ifmo.ru/~<логин>/`.

| Механизм | На Helios | Обоснование |
|---|---|---|
| Статический HTML, CSS, JS, поиск Material/Sphinx | да | поиск работает на клиенте по `search_index.json` / `searchindex.js` |
| Формулы и графики без интернета | да | MathJax и Plotly.js лежат в самом сайте |
| Мета-теги Highwire, DC, OG | да | это часть HTML, хостинг не влияет |
| `sitemap.xml` | частично | файл публикуется, но его надо регистрировать в Search Console вручную: сослаться на него из `robots.txt` нельзя |
| `robots.txt` | **нет** | роботы читают только `/robots.txt` корня домена `se.ifmo.ru`, пользователь не управляет им |
| Постоянный URL | **нет** | адрес привязан к учётной записи студента и перестаёт существовать после её удаления |
| Собственный домен | **нет** | виртуальные хосты для пользователей не предоставляются |
| HTTPS | да, но не под контролем пользователя | сертификат домена `se.ifmo.ru` |
| Серверные редиректы 301 | не гарантированно | зависят от разрешения `.htaccess`; переносимый вариант — HTML-страницы с `meta refresh` |
| Версии `/v1.0/`, `/latest/` | да | это просто подкаталоги; `versions.json` от `mike` работает на любом статическом хостинге |
| DOI, указывающий на сайт | не рекомендуется | DOI должен вести на долговременный ресурс; на Helios его нет, поэтому DOI — на Zenodo |
| Индексация Google Scholar | маловероятна | персональные каталоги на учебном сервере индексируются хуже, чем Zenodo |

Итог: Helios подходит как **зеркало** и площадка для демонстрации
в отечественной инфраструктуре, но не как место «канонической» публикации.
Канонический адрес — GitHub Pages (или собственный домен), долговременное
хранение и DOI — Zenodo.

## 10. Вывод по T5

Сайт с результатами становится публикацией, когда выполнены три условия:
результат **идентифицируем** (DOI и ORCID), **неизменяем для
процитированной версии** (версии сайта + метка коммита и данных) и
**машиночитаем** (Highwire/DC/OG, sitemap, CFF, раздельные лицензии).
Генератор обеспечивает только третье условие и частично второе;
первое — задача внешней инфраструктуры (Zenodo, ORCID).
Из рассмотренных генераторов больше всего «из коробки» даёт Quarto,
из Python-генераторов — MkDocs + Material, где недостающее
добавляется одним override-шаблоном и плагином `mike`.
